1. Camada de Rede & Gestão de Topologia
Esta componente implementa a espinha dorsal da rede Ad-Hoc sobre Bluetooth BLE, orquestrando a lógica de conectividade em node_main.py. A arquitetura segue uma topologia em árvore dinâmica com estratégia "Lazy": os nós exploram o ambiente através de scans periódicos (common/scan.py), selecionando automaticamente o Uplink que anuncia a menor distância (hops) até ao Sink (common/manageConnections.py).
Para garantir a resiliência da rede (Network Liveness), foi implementado um gestor de vivacidade (node/heartbeat_manager.py) que monitoriza a receção de pacotes de heartbeat. O sistema tolera perdas pontuais, mas, após 3 falhas consecutivas, declara o Uplink como inoperante, desencadeando o corte imediato da conexão e o reinício autónomo do processo de descoberta para restabelecer a rota.

2. Infraestrutura de Segurança & Comunicação 
Esta área estabelece a base de confiança do sistema. A segurança suporta-se numa PKI personalizada, utilizando certificados X.509 e Criptografia de Curva Elíptica (ECC) para garantir robustez com chaves de tamanho reduzido, otimizadas para o MTU do BLE. A autenticação é mútua e ocorre imediatamente após a conexão física: o ConnectionManager executa um handshake onde são trocados certificados através de pacotes de controlo HELLO, prevenindo a injeção de tráfego por nós não autorizados.
Ao nível da infraestrutura Linux, foi desenvolvida uma camada de abstração de Servidor GATT sobre DBus (common/gatt_server.py). Esta implementação crítica ultrapassa as limitações de sockets padrão, utilizando o mecanismo de sinais PropertiesChanged para permitir uma comunicação bidirecional fluida e assíncrona entre os dispositivos e a stack BlueZ.

3. Encaminhamento Seguro e Serviços End-to-End
Esta componente assegura a proteção dos dados em trânsito. O encaminhamento (Routing) em node/router.py implementa uma tabela de encaminhamento dinâmica protegida salto-a-salto: cada ligação utiliza uma chave de sessão única, negociada via ECDH, para cifrar todo o tráfego com AES-GCM (common/security.py). Este método garante confidencialidade, integridade e proteção contra ataques de Replay (através da validação estrita de números de sequência).
Adicionalmente, foi criada uma camada de segurança Fim-a-Fim (common/dtls.py) que estabelece um túnel cifrado virtual entre cada Nó e o Sink, isolando os dados da aplicação (Inbox) de quaisquer intermediários. A operação é gerida através de uma Interface de Utilizador (CLI) em node_main.py, que permite a visualização em tempo real da topologia e a injeção de falhas controladas (bloqueio de heartbeats) para demonstração de robustez.

4. Nota sobre a Implementação e DTLS
Todas as funcionalidades críticas do enunciado foram implementadas, com destaque para a segurança em profundidade (Defense in Depth).
Relativamente ao requisito DTLS: Em conformidade com as restrições técnicas de implementar protocolos baseados em UDP sobre BLE em userspace, a solução adota uma abordagem "DTLS-like" aplicacional. Em vez de utilizar bibliotecas OpenSSL (incompatíveis com a arquitetura GATT/DBus sem encapsulamento IP completo), foi desenvolvida uma stack criptográfica em Python (DTLSManager) que replica os mecanismos de segurança do standard: Handshake dedicado, troca de chaves e cifragem autenticada do payload, garantindo as mesmas propriedades de segurança exigidas (Confidencialidade, Integridade e Autenticidade).
